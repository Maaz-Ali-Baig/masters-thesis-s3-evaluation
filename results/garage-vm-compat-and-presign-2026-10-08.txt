2. Presigned PUT with unsigned x-amz headers (CVE-2026-54330 vector)
--------------------------------------------------------------------
Raw file on ceph0: 85 lines, 5667 bytes, sha256 c19e0f874d39208dfa116dd655b3d2b93b9f0c47951e08901236e3270db2d8b7
(/root/presign-garage-vm-20261008-142536/run/security-presign-unsigned-header-garage-vm-20261008-142537.txt).
The laptop file has 85 lines and 5664 bytes (the three extra bytes are "garage-vm" against "garage" in the header).
Comparison method, the same awk on both files: drop the header, date and bucket lines, print only the case id on
case lines, squeeze spaces and cut every other line to 45 characters. Result: 82 lines each. The hashes differ,
laptop 27587da3eb69a3515030aeb45e534dd3ee4fe4eb01c49d1543157ed30382fb18, VMs c6c14f85b7516dfa29fe9d60f629a01199bca536bcf664729dfef3b04ec2d9ea.
If the four lines "acl, own credentials HTTP 501" of the laptop view are changed to "HTTP 403", the hash of the
laptop view is exactly c6c14f85...d9ea. So the two runs differ in nothing else within the compared text.
Same on both: g0, p0, p1, s2 and s3 answer HTTP 200 (controls and the Content-Type case); p2 to p8 (unsigned
x-amz-meta, acl, tagging, storage class, website redirect, copy source from the same bucket and from another
bucket) answer HTTP 400 InvalidRequest "Header ... should be signed"; the cleanup deletes answer HTTP 204.
Difference: the ACL read of the control objects (p0, p1, s2, s3) answers HTTP 403 on the VMs
(<Error><Code>AccessDenied</Code><Message>Forbidden: Invalid signature) and HTTP 501 NotImplemented on the laptop.
PROVEN: Garage v1.0.0 on the VMs rejects every unsigned header case, as the laptop single node did.

The 403 on the ACL read, settled the same day on ceph0 (hostname debian, a temporary bucket with one object, removed
afterwards, key never printed). Hypothesis H3 was: the 403 is caused by the client on ceph0 (curl 7.88.1, laptop
curl 8.5.0), not by Garage. Result, each request signed by curl --aws-sigv4 with the header x-amz-content-sha256 of
the empty body, except the AWS CLI line:
  curl GET of the key, no query            HTTP 200
  curl GET <key>?acl                       HTTP 403 AccessDenied "Forbidden: Invalid signature"  (the form the script sends)
  curl GET <key>?acl=                      HTTP 501 NotImplemented "Unimplemented action: GetObjectAcl"
  aws s3api get-object-acl (CLI 2.36.8)    NotImplemented "Unimplemented action: GetObjectAcl"
(A first attempt without the x-amz-content-sha256 header answered 400 "Missing X-Amz-Content-Sha256 field" for both
curl forms. That was a mistake in my test command and says nothing about ACLs.)
PROVEN: Garage on the three node cluster answers an ACL read with 501 NotImplemented, as on the laptop. The 403 is
produced by curl 7.88.1 on ceph0 when the query parameter has no value (?acl): the same request with ?acl= is
accepted. So the three node cluster is not the cause, and the ACL lines of the VM presign file (403) are an artifact
of the client on ceph0.
NOT PROVEN: that curl 8.5.0 signs ?acl correctly (the laptop run answering 501 is consistent with it, the curl
source was not read, and the laptop was not retested). NOT PROVEN for Ceph: the Ceph record O6 (ACL read answers 403
SignatureDoesNotMatch on Ceph in p0, s2, s3) shows the same pattern with the same client, but the Ceph cluster is
stopped, so O6 stays open. Settling test for O6 when Ceph runs again: the ACL read with ?acl=.
CONSEQUENCE: the scripts send ?acl, so on ceph0 every ACL read through curl is unreliable until the scripts send
?acl= (the form the AWS CLI sends). Changing the scripts changes the comparison with the laptop runs and needs a
decision. The verdicts in section 1 (AWS CLI) are not affected, the presign verdicts p2 to p8 (400) are not affected.
