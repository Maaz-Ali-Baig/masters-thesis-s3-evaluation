==========================================================================================================

Follows results/seaweedfs-vm-performance-2026-10-12.txt (same series, same output folder name /root/perf-seaweedfs-20261012-223312 on the three nodes).
It reads the sar logs (sar -u -r -d -n DEV, one sample per second, recorded on each node during the whole series by scripts/perf-warp.sh).

S1. Disk write volume against client throughput (sum of wr_MiBs divided by the client MiB/s of the performance record):
      100 MiB 661.2 / 231.81 = 2.85;  16 MiB 628.2 / 233.67 = 2.69;  1 MiB at concurrency 1: 95.5 / 34.88 = 2.74;  c4 296.2 / 120.96 = 2.45;

    The cause is NOT known (see open questions Q1).
S2. Disk read volume against client throughput for GET (sum of rd_MiBs over the three nodes divided by client MiB/s):
      100 MiB 1056.9 / 1302.15 = 0.81;  16 MiB 608.4 / 1302.95 = 0.47;  50 KiB 6.9 / 193.46 = 0.04

    concurrency 4, 59 percent at 1), 47 percent at 16 MiB, 81 percent at 100 MiB. So a large part of the data did not come from the drives in the run window (it came from memory, or the nodes served it
    without a read that sar -d counts). At 1 MiB the read rate per node is nearly the same for concurrency 8, 16 and 64 (64.1, 63.7, 63.9 MiB/s on ceph1) while the
    client rate changes from 1125 to 1283 MiB/s; cause not examined (Q2).
S3. Network at the load node ceph2 (receive): GET 100 MiB 942.8 MiB/s (7.91 Gbit/s), GET 16 MiB 930.2 (7.80), GET 1 MiB c16 984.6 (8.26), c64 901.6 (7.56), c8 880.8 (7.39);

OPEN QUESTIONS (hypotheses, with the test that settles them; not findings)
--------------------------------------------------------------------------
Q1. Why do the drives write less than three times the client volume at 1 MiB from concurrency 8 and only 1.06 times at 50 KiB? Candidates: (a) writes stay in the page cache
    and are flushed after the end of the run window; (b) not all three copies are written in the window; (c) the sar device rates do not count part of the writes.
    Settles: the volume size growth per node (volume status Size of the collection) and the kernel counters of written bytes (/proc/diskstats) before and after one PUT run, compared
    with the client bytes; /proc/meminfo Dirty during a run.
Q2. Why is the disk read rate per node constant at about 64 MiB/s for 1 MiB GET from concurrency 4 to 64? Settles: per run values, sar -d await and utilisation, a run with
    the page cache emptied during the run.
Q3. Is one core of ceph2 saturated in the PUT runs at 1 MiB? Settles: sar -P ALL (not recorded in this series; add to the script for the next system if kept).
Q4. Part of the GET data of ceph2 is read locally (ceph2 holds a copy of every volume with replication 002), which would explain why its receive rate is below the client rate
    (S3). Not proven. Settles: a GET run with a client on a fifth VM, or the volume server request counters per node.

STATUS OF THE HYPOTHESES OF THE PERFORMANCE RECORD
--------------------------------------------------
H2 (GET partly from page cache): SUPPORTED for all GET configurations (S2), the largest share for 1 MiB from concurrency 8 and for 50 KiB (drives delivered 4 percent and 15 to 17 percent of the
   client volume). So all GET numbers of this series must be labelled as measurements with a large cache share, in particular GET 1 MiB and 50 KiB.
H3 (common cause of the PUT plateau): OPEN. For 1 MiB no node is saturated by mean CPU, iowait or network (S5), for 16 and 100 MiB the load node is above 90 percent (S4) and the numbers are
   client limited by the rule of the method.
H1 and H4: not tested by these data.

LIMITS
------
L1. The load node is also a storage node, and in three configurations it is above 80 percent CPU (S4).
L2. sar %util, await and queue depth are not in the table (only rates), so a drive saturation cannot be excluded or shown here. Per core CPU is not in the table (Q3).
L3. The windows are the whole Warp process, so rates and ratios are approximate (about 10 percent).
L4. Means of three runs per configuration; single run values are only in the per run tables on the nodes.
L5. The vacuum calls before the runs (performance record, section SPACE) produce disk and CPU activity between the runs; they are outside the run windows but their effect
    on the page cache or on the following run was not measured.
