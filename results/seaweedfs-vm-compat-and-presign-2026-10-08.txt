3. The 403 on the ACL read, settled the same day on ceph0
---------------------------------------------------------
Hypothesis H3 (as for Garage): the 403 is caused by the client on ceph0 (curl 7.88.1), not by SeaweedFS. Test on ceph0, a
temporary bucket with one object (removed afterwards, cleanup rc 0, key never printed), each request signed by
curl --aws-sigv4 with the header x-amz-content-sha256 of the empty body, except the AWS CLI line:
  curl GET of the key, no query            HTTP 200 (body "hi")
  curl GET <key>?acl                       HTTP 403 SignatureDoesNotMatch ("The request ..." cut at 100 characters)
  curl GET <key>?acl=                      HTTP 200 AccessControlPolicy, Owner admin
  aws s3api get-object-acl (CLI 2.36.8)    answered with Owner admin and a Grants list
PROVEN: SeaweedFS answers the ACL read correctly. The 403 is produced when curl 7.88.1 sends the query parameter without
a value (?acl): the same request with ?acl= is accepted, and so is the AWS CLI. So the three node cluster is not the
cause, and the ACL lines of the VM presign file (403) are an artifact of the client on ceph0. This is the same pattern as
for Garage (403 on ?acl, 501 on ?acl=).
NOT PROVEN: that curl 8.5.0 signs ?acl correctly (the laptop answering 200 is consistent with it, the curl source was not
read, and the laptop was not retested). NOT PROVEN for Ceph: the Ceph record O6 (ACL read answers 403 SignatureDoesNotMatch
in p0, s2, s3) shows the same pattern with the same client, but the Ceph cluster is stopped, so O6 stays open. Settling
test for O6 when Ceph runs again: the ACL read with ?acl=.
CONSEQUENCE: the scripts send ?acl, so on ceph0 every ACL read through curl is unreliable until the scripts send ?acl=
(the form the AWS CLI sends). Changing the scripts changes the comparison with the laptop runs and needs a decision. The
verdicts in section 1 (AWS CLI) are not affected, the presign verdicts p2 to p8 are not affected.
