PROVEN (read from the output above)
-----------------------------------
S1-P1. No acknowledged write was lost in this run: all 1179 acknowledged probe objects and all 45 seed objects are readable through every endpoint, including
       the restarted node, with the recorded sha256.
S1-P2. With one of three nodes (two of six drives) stopped, writes and reads through the other nodes continued: 172 probe objects were acknowledged and the
       seed set read back OK through ceph0 during the outage.
S1-P3. Client visible interruptions were short and limited to the moments around the stop and the restart: 34 failed write attempts in 12 minutes and a longest
       gap of 26.8 s between acknowledged writes. The 34 failures lie between 15:02:47 and 15:14:55 (the node was down from about 15:02 to 15:15); that they
       are attempts to the stopped node is consistent with the script logic (rotating first endpoint, next endpoint after a failure) but the error text of the
       ledger rows was not read here.
S1-P4. The restarted node serves S3 requests again 60 s after the power on signal (ssh 57 s after the signal, S3 answer at 15:15:08, with the start command run by the script).
       The user pressed Start some seconds after the signal, so the boot itself took a little less than this.
S1-P5. After the run each of the six drives holds the same number of files and bytes for the probe objects, including the 172 objects written while ceph1 was down.
       So the shards that ceph1 missed during the outage are present on its drives at about 16:05.

FINDINGS FOR THE THESIS
-----------------------
F-S1-1. RustFS does not start by itself after a node reboot in this deployment: after the power on of 11 October 14:3x the container list of ceph1 had Ceph
        containers only and the S3 port 9000 did not answer (health 000, read through ceph0). In S1 the script had to run the node start script. Cause (no
        restart policy or no boot service) not examined.
F-S1-2. The Ceph daemons on the same VMs start by themselves after a power on (cephadm target enabled). This matters for any fault test of another system on
        these VMs and was handled for ceph1 by disabling the target (to be undone before the Ceph phase, see setup_notes.md).

NOT PROVEN, hypotheses and open points (not to be written as findings)
----------------------------------------------------------------------
O1. When the missing shards on ceph1 were restored is not measured. The data size reading of the script (du of the whole data folder every 20 s) is noisy
    while the probe writes (examples read from the screen: ceph1 minus ceph0 was +12.7 MB at the first sample before the outage, +77 MB at 15:16:32, +76 MB
    at 15:18:36, -2 MB at 15:20:39, +102 MB at 15:24:47, +6 MB at 15:37 to 15:43; the values of all three nodes also moved up and down by tens of MB between samples).
    It does not show a recovery time. Because the data size was never constant while the probe ran, the script's rule "stop after 180 s of stable size"
    could not fire and the watch ran into its 30 minute limit (hypothesis for the reason; the sizes were read, the rule was read in the code).
    Settles: a repeat that counts the files under ftbucket/probe per drive every 20 s (as in the check above) and the RustFS healing status if it has one.
O2. Whether the equal state of the six drives came from background healing or from the reads of the full verification (a read may repair; not known for
    RustFS) is open. Settles: the per drive count before the full verification, in a repeat or in S2.
O3. Cause of the 26.8 s gap and of the 28 s between "silent" at 15:02:08 (script) and 15:02:36 (probe): hypothesis that a write in flight to the stopping node waited
    for a timeout and delayed the probe loop (the first probe sample after the stop is also at 15:02:36). Settles: the ledger and probe rows around 15:02 (not read).
O4. Two nodes stopped (S2) has not been run. The hypothesis of the method (with two of three nodes down the cluster cannot write and may not read) is untested.
O5. Planned restart of a node (S3) is optional and not run.

LIMITS
------
L1. Light load: one 1 MiB write every 2 s (about 0.5 MiB/s of client data); 172 MiB were written while ceph1 was down. The time and effort of restoring
    shards depend on this volume, so the result is not a statement about heavy write loads.
L2. One run, one day, one node, one outage length (12 minutes). No repetition and no statistics.
L3. The script printed "D: unbound variable" once at its end. The exit handler uses the variable D, which is local to the scenario function (hypothesis; the line
    was read in ft.sh). All results had been written before. The script was not changed, so the cited commit is the script that ran.
L4. The stop and the power on are done by a person in Proxmox. The reaction time is inside the numbers (39 s between the signal and the silence of the endpoint).
L5. Reads during the outage were checked through the surviving endpoint 192.168.1.72 only (script design), not through ceph2.
L6. Redundancy differs between the systems (erasure coding 3+3 against three copies in the others), so a result for RustFS is not comparable one to one.
L7. The archive and the tsv files stay on the VM (ceph0) and in the archive, the numbers here are read from the screen.
