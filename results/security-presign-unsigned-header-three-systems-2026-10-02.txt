QUESTION
--------
A presigned PUT URL is signed with SignedHeaders=host. If a client adds further x-amz-* headers that the
signature does not cover, does the server reject the request, or does it accept it, and does it then act on
those headers? AWS SigV4 says such a request must be rejected. Ceph fixed exactly this class of flaw in
CVE-2026-54330 (Tentacle 20.2.4), which is why the question matters for the comparison.

METHOD
------
Every case sends one presigned PUT built from the same signing code, with one change per case, and removes the
Content-Type that curl would add on its own, so only the named header differs. After an accepted upload the
object is read back with the owner's credentials (HEAD, ACL, content) and with an anonymous GET.
Controls: g0 (a presigned GET of an existing object, proves the signing code is right), p0 (nothing extra),
s2 and s3 (the metadata header and the ACL header put inside the signature).

PROVEN (quoted evidence in the raw files)
-----------------------------------------
1. RustFS accepts every unsigned x-amz-* header in the test with HTTP 200 and acts on five of them.
   Read back with the owner's credentials:
     p2  HEAD shows "x-amz-meta-injected: yes" (p0 shows no such header).
     p4  HEAD shows "x-amz-tagging-count: 1".
     p5  HEAD shows "x-amz-storage-class: STANDARD_IA".
     p6  HEAD shows "x-amz-website-redirect-location: https://example.org/".
     p7  The PUT reply is a <CopyObjectResult>, the request body was empty, and the object read back has
         content-length 19 and the content "presigned put body", which is the content of g0.
     p8  The same with a source in a second bucket: content-length 25, content "cross bucket source body",
         which is the content of secret.txt in the other bucket (a different length and text than g0, so
         the copy cannot come from anywhere else).
2. RustFS accepts x-amz-acl: public-read and does not apply it, signed or unsigned. For p3 and for the
   signed control s3 the ACL read back has 0 AllUsers grants and an anonymous GET gives 403. So the ACL
   header has no effect in either form.
3. SeaweedFS rejects p2 to p8 with 403 SignatureDoesNotMatch and Garage rejects them with 400 InvalidRequest
   naming the header that "should be signed". The script reads nothing back after a rejected PUT, so
   whether an object was left behind is not checked. Both accept the signed controls s2 and s3.
4. All three accept an unsigned Content-Type. SeaweedFS and Garage apply it (SeaweedFS stores
   application/octet-stream for p1 and text/plain; charset=utf-8 for p0, Garage stores
   content-type: application/octet-stream for p1 and none for p0). AWS also tolerates an unsigned
   non x-amz header, so this is normal. Ceph 20.2.4 rejects it with 403 (results/s3-compat-ceph-2026-10-02.txt),
   so Ceph is stricter than AWS here.
5. The signing code is correct: g0 is 200 on all three, and the signed controls s2 and s3 are accepted, so
   the rejections in point 3 are caused by the unsigned header and not by a faulty signature.

HYPOTHESES (not settled, do not cite as findings)
-------------------------------------------------
H1. RustFS builds its signature check from the SignedHeaders list only, which would explain why it ignores
    extra headers. The RustFS source at the tested image was not read.
    Settling test: read the verifier in the source of the exact version.
H2. Ceph 20.2.4 rejects p2 to p8, as the CVE fix says. Not tested in this laptop run. SETTLED on
    5 October 2026: the Ceph run rejects all of them, see the Ceph record.

OPEN
----
O1. Whether the RustFS behaviour is a privilege escalation. In this test the signer is the admin identity and
    can read the source bucket anyway, so p8 shows that the header is acted upon, not that a permission
    was bypassed. Settling test: a scoped identity that has no read access to the second bucket signs the
    URL. If the copy from the second bucket still succeeds, the server does not check the signer's
    permission on the source.
O2. Ceph run on the VM: done on 5 October (the Ceph column is in the Ceph record). Still open: the repeat of
    the three laptop systems on the VMs.
O3. Whether RustFS applies an unsigned Content-Type: p0 and p1 both store application/octet-stream, so the
    test cannot tell. Settling test: send a distinct value, for example text/x-test, and compare.
O4. RustFS is a beta (1.0.0-beta.8). Its behaviour here may change in a later release, and it must not be
    read as a statement about a stable RustFS release.
O5. Single node containers on a laptop, one run each. The behaviours above are rejections and
    acceptances of requests, so repetition is unlikely to change them, but it was not repeated.

PROCESS NOTES
-------------
- curl adds an unsigned Content-Type on its own when it sends a body. The script removes it with
  -H "Content-Type:" in every case, otherwise Ceph would refuse every request for that reason (see the
  Ceph record) and the test would not show the header under study.
- The classification of a case is read from the raw files by a person. The script prints, it does not judge.
