PROVEN (read from the output above)
-----------------------------------
SE-P1. The S3 port refuses requests without a valid signature: anonymous GET, PUT and DELETE return 403; a wrong secret gives SignatureDoesNotMatch; an unknown access key
       gives InvalidAccessKeyId.
SE-P2. Without credentials the nodes answer with information: /health shows the service name and the exact version (1.0.1), /minio/health/cluster shows readiness details of
       storage, IAM and lock and the list of degraded reasons, and port 9001 serves the web console page to anyone who can reach it (on every node).
SE-P3. An object stored without server side encryption is readable in clear in a file on the data drives (the marker text was found in xl.meta of the plain object on one
       drive of each node, so on three of the six drives).
SE-P4. For the SSE-S3 and the SSE-C object the marker text was not found in any file under the data folders of the three nodes.
SE-P5. A failed authentication attempt with a made up access key leaves no line in the container log of any node at the default log level.
SE-P6. The S3 port is plain http here (all requests of the run used http://).

NOT PROVEN, hypotheses and open points (not to be written as findings)
----------------------------------------------------------------------
SE-O1. Why the marker is on three drives and in xl.meta: hypothesis that small objects are stored inline in xl.meta and that the three data shards hold the plain text while the
       three parity shards hold coded bytes. Settles: the RustFS documentation or source and a look at the files (not done).
SE-O2. The absence of the marker in the SSE objects shows only that the text is not stored in clear in the searched folders (a clear copy would have left 400 copies of the
       marker). It says nothing about the strength of the encryption or about where the keys are kept.
SE-O3. The web console login and what the console allows without credentials are not tested (SEC7 of the method): only the static page is shown to be public.
SE-O4. Whether the exposed health and cluster paths can be switched off, and whether the failed attempts can be logged at a higher log level, is not examined.
SE-O5. Transport encryption on the wire (SEC5) was not tested in the run of 11 October (tcpdump missing); it was tested on 12 October, see the ADDENDUM below. Open
       there: why the capture shows 264 marker lines for 200 uploaded, and whether RustFS can be configured for TLS.
SE-O6. A scoped key (SEC4) is not tested, so nothing is stated about bucket level permissions.
SE-O7. The comparison with the other three systems follows when they are run with the same script.

ADDENDUM 12 October 2026: SEC5 transport (wire test)
====================================================
Setup:     tcpdump was installed on ceph0 by the user on 12 October (checked at 10:08 CEST: absent; at 10:23: /usr/bin/tcpdump, version 4.99.3). Same script as above
           (scripts/sec.sh at commit 73b28e8, same sha256), run on ceph0 as "bash /root/sec-deploy/sec.sh rustfs sec5" at 10:23:51 (VM clock, UTC+2).
Method:    the script writes a file of 200 lines of one marker text (SECPROBE-WIRE-MARKER-<time>-ABCDEFGHIJKLMNOP), starts tcpdump on ceph0 (interface any, filter host and
           port of the target), uploads the file with the AWS CLI to 192.168.1.71:9000 (ceph1, over http), stops the capture after 2 s and counts with grep -c -a the lines of the
           capture file that contain the marker. The test object and the capture are deleted afterwards (the capture holds the access key id in the Authorization header).
Result (read from the console of the VM session, the same text is in sec5.txt, which the second command printed):
           "marker lines found in the capture: 264  (above 0 means the content crossed the network in clear)". Secret key found in the output files: 0, access key found: 0.
Output:    on ceph0 /root/sec-rustfs-20261012-102351/ (sec5.txt, summary.txt, SHA256SUMS) and /root/sec-rustfs-20261012-102351.tar.gz (643 bytes, sha256
           650e32acb968dca3daebc1aeca3391b39c83d64b7fa3c4542d50e15f4800dc85, typed from the screen and checked by a second command on ceph0: sha256sum of the archive piped to
           grep -c with this string gave 1).

PROVEN
SE-P7. The content of an object uploaded without server side encryption to the S3 port of a RustFS 1.0.1 node (port 9000, plain http) is visible in clear in the network
       traffic between two nodes: the marker text was found in the capture taken on the sending node (count 264, above 0).

NOT PROVEN
SE-O8. Why the count (264) is higher than the 200 uploaded lines. grep -c counts lines of the binary capture file that contain the marker, not lines sent; hypothesis: the
       count of a binary file depends on packet splitting and on duplicates (retransmissions or the interface any), not examined. The result "above 0" does not depend on it.
SE-O9. Whether RustFS can serve TLS on port 9000 and what it takes to configure it; the test shows only the state of this deployment (no TLS configured). Settles: the RustFS
       documentation and a test with a certificate (not done).
SE-O10. The test used the default upload (no SSE header); whether an SSE-S3 upload is encrypted on the wire is not the question here (SSE protects the stored object, the
        transport is plain http either way as far as SE-P6 shows), and it was not captured.
SE-O11. Only one direction was captured (ceph0 to ceph1, on ceph0), one upload of about 13.8 KB (200 lines of 69 bytes, arithmetic mine), one run.
