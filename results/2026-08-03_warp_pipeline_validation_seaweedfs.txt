before and after each run. A dedicated warp-benchmark-bucket is used so that
thesis-test-bucket is never touched.

================================================================================
OBSERVATIONS
================================================================================

1. RESULT: 1732 requests, 0 errors. The measurement chain works end to end.

2. MEASURED WINDOW SHORTER THAN REQUESTED. Warp reported "Ran: 16s" for a
   --duration of 20s, because it trims ramp-up and ramp-down from its analysis
   window. Durations reported in the thesis must be the measured window.

3. HIGH VARIANCE WITHIN A SINGLE RUN. Per-second throughput ranged from
   48.9 to 168.6 MiB/s, a factor of 3.4. Latency standard deviation (42.3 ms)
   is close to the mean (46.2 ms), and p99 (197 ms) is five times p50 (39 ms).

   Probable causes are environmental rather than properties of SeaweedFS:
   Docker Desktop virtualisation, the Windows host filesystem underneath,
   on-demand volume allocation inside SeaweedFS during the run, and no warm-up.

   This is direct empirical justification for repeating every measurement at
   least five times: reporting this single run as "94.52 MiB/s" would have been
   indistinguishable from a run that happened to average 49 or 169 MiB/s.

4. IMPLICATIONS FOR THE MEASUREMENT PROTOCOL (to raise with the professor
   before data collection begins, as these are protocol changes):
     - add an explicit warm-up phase whose results are discarded
     - use longer runs (e.g. 60 s) in addition to repetition
     - record host state alongside each result set
