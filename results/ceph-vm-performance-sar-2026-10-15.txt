Ceph 20.2.4, three nodes on the VMs: resource use during the performance series (15 October 2026)
===============================================================================================

Follows results/ceph-vm-performance-2026-10-15.txt (same series, output folder /root/perf-ceph-20261015-103411 on the three nodes).
It reads the sar logs (sar -u -r -d -n DEV, one sample per second, recorded on each node during the whole series by scripts/perf-warp.sh).

Method:    scripts/perf-sar.sh, sha256 3f51a415eb503976fb89a7fd84270dd22c25d2885ea07d7c4d7a8c36595a6d6a (the copy in /root/perf-deploy3 on ceph2, copied to ceph0 and ceph1 by scp; the hash printed on
           each of the three nodes was equal). Run on 15 October on the three nodes, each in the output folder of the series on that node; the file runs.tsv was copied from ceph2 into the folders
           of ceph0 and ceph1 first. For every recorded run (51) the script averages the sar samples between the start and the end of the Warp process (epochs from runs.tsv). The window is the whole
           Warp process, which is longer than the 60 s measured window for PUT (as in the Garage record), so rates and ratios of PUT runs are not rates of the measured minute.
           Columns: cpu_busy (100 minus idle of the line "all", percent), iowait (percent), rd_MiBs and wr_MiBs (disk read and write rate summed over the data disks, system disk excluded), net_rx_MiBs and
           net_tx_MiBs (the interface that is not lo, MiB/s), samples (seconds in the window). Which devices the script counted as data disks (device names) was not read from the screen in this
           session; the OSD disks are the two data disks per VM of the cluster.
Per run tables (51 runs each, header line included, 52 lines), typed from the VM screen into these files; the sha256 of every file equals the sha256 printed by the VM for its own file (compared, equal;
           the first typing of the ceph0 file had two wrong values, found by comparing a checksum per line with the VM and corrected, the VM file was not changed):

PROVEN (read from the tables, arithmetic mine; sums are over the three nodes)
----------------------------------------------------------------------------
S1. Written volume of the drives in the window of a PUT run against the client volume of the measured minute (sum over the nodes of wr_MiBs times samples, divided by client MiB/s times 60 s). Mean of the
    three runs: 100 MiB 3.05; 16 MiB 3.03; 1 MiB at concurrency 1: 3.08, 4: 3.08, 8: 3.08, 16: 3.07, 64: 3.07; 50 KiB 7.81. Three copies would give 3.0. The window is longer than the measured minute,
    so the ratios are up to a few percent off in either direction. For comparison, the same calculation for Garage gave 3.5 to 3.7 (1 MiB and larger), about 6 at one user and about 7.5 at 50 KiB
    (results/garage-vm-performance-sar-2026-10-13.txt); I did not recompute the other systems here.
S2. Read volume of the drives against the client volume in the GET runs (same calculation with rd_MiBs): 1 MiB 0.41 (c4), 0.41 (c8), 0.43 (c16), 0.43 (c64), 0.47 (c1); 16 MiB 0.75; 100 MiB 0.75; 50 KiB 0.01.
    The cause is OPEN (question Q1 of the performance record; a cache is a hypothesis).
S3. CPU (cpu_busy, mean of the three runs of a configuration), ceph0 / ceph1 / ceph2: PUT 50 KiB 64.4 / 62.8 / 67.2; GET 50 KiB 37.8 / 36.6 / 32.9; PUT 1 MiB 53.0 / 52.3 / 77.2; GET 1 MiB 28.4 / 28.2 / 60.4;
