PROVEN (read from the output above)
-----------------------------------
SW-P1. The S3 port 8333 refuses requests without a valid signature: anonymous GET, PUT and DELETE return 403, a wrong secret gives SignatureDoesNotMatch, an unknown access key InvalidAccessKeyId.
SW-P2. Without credentials, every node answers with information on the master, volume server and filer ports: the master page, the cluster status (leader and peers) and the topology (/dir/status), the volume
       server status page, the filer root page, and a lookup of the volume servers of a volume.
SW-P3. Writes without credentials are refused on the filer (401), on the volume server (401) and on the master (404); the master hands out file ids to anonymous requests (assign), but an upload with such an
       id was refused (401).
SW-P4. The content of stored objects can be read WITHOUT any credential through the filer port 8888 of every node: the seed object 1MiB-1 (1 MiB) was downloaded anonymously from all three nodes with a sha256 equal
       to the stored one, and fixed/head.bin (1024 bytes) answered 200 on all three; the buckets and their metadata are listed anonymously (JSON). So the S3 authentication does not protect the data
       in this deployment against a client that can reach port 8888 (the filer read does not need the S3 key; setup_notes.md records a signing key under [jwt.filer_signing] in security.toml, the file was not re-read).
SW-P5. The S3 traffic is plain http, and the content of an uploaded object is visible in the network traffic between two nodes (marker found in the capture, count 199 for 200 lines).
SW-P6. An object stored without server side encryption is readable in clear in the volume file on the data drives: with random padding around the marker (run 3) the marker text was found in
       /srv/s3/disk2/seaweedfs/ftbucket_69.dat on all three nodes (4 occurrences on ceph1 and ceph2, one file per node), so the data of the replicas (three copies) is in clear.
SW-P7. The SSE-C object was not found in clear (4 occurrences in the volume file of ceph1 and ceph2, 4 are the 4 marker lines of the one plain object; arithmetic mine: an SSE-C object in clear would add
       4 more). SSE-S3 (--sse AES256) is refused with InternalError on this deployment, in all three runs.
SW-P8. A failed authentication with a made up access key IS written to the container log of the node that served it, at the default log level (2 lines on ceph0, "InvalidAccessKeyId: attempted key ... not
       found", level W), not on the two other nodes (they did not serve the request). The log is not empty: this also corrects the statement "the logs of the containers were empty" in the fault tolerance
       records of 13 October (see the correction there).

NOT PROVEN, hypotheses and open points (not to be written as findings)
----------------------------------------------------------------------
SW-O1. Why run 1 and run 2 found the marker in no file although the plain object was stored: hypothesis that SeaweedFS compresses repetitive data before it writes it (the marker of run 3 appears as
       it is when the data is random around it). Not shown (no look at the volume server code or a size comparison).
SW-O2. Why writes through the filer need a token (401) but reads do not: hypothesis that only the write signing key is set (setup_notes.md records [jwt.filer_signing]) and that a read signing key is not
       set. Not tested (a test needs a changed security.toml and a restart of the three containers). Whether a hardened configuration (read signing key, filer not reachable from the network) closes the
       anonymous read is open.
SW-O3. Why SSE-S3 is refused with InternalError (missing KMS or key configuration, a limit of 4.25 with this configuration?). Not examined. Where the SSE-C key is kept and how it is checked is not examined.
SW-O4. The anonymous reads through the filer were tested for two objects of ftbucket (1 MiB seed object, 1 KiB fixed object). Other buckets and objects were not read; the list of buckets shows what
       exists. Whether an anonymous client can also change or delete data through other filer paths (for example the filer admin, the master /vol and /col paths or the shell ports) is NOT tested on purpose
       (a destructive test on the data of the other runs); the master answers anonymous /cluster/status and /dir/status.
SW-O5. The ports 631 and 8181 and the gRPC ports 18080, 18333, 18888, 19333 were not tested for anonymous access.
SW-O6. SEC4 (a scoped key that may read only one bucket) is not tested; nothing is said about bucket level permissions. SEC7 (admin interfaces) is limited to the unauthenticated answers listed above.
SW-O7. Whether SeaweedFS can serve TLS on the S3 and the filer ports and what it takes (level 2 of SEC5, time box) is not tested.
SW-O8. Why the capture shows 199 and not 200 marker lines (the RustFS run counted 264): packet boundaries; same hypothesis as for RustFS (SE-O8 there). Not examined.

LIMITS
------
L1. All checks ran from ceph0 against its own endpoint 192.168.1.72 (sec3, sec6 against 8333; the anonymous list and the filer reads against all three nodes). One day, one version (4.25), default log level, the
    deployment of 12 October (security.toml with the write signing key only), after the fault tolerance runs of the same day.
L2. The test objects are deleted at the end of each check, but the marker text of the plain object stays in ftbucket_69.dat on the three nodes until a vacuum or compaction removes it (the data of
    deleted objects is not erased at once; not examined). The data in the bucket ftbucket is test data of this thesis only.
L3. The anonymous path list of sec1 is fixed (15 paths per node); other paths may answer too. In run 2 sec2 printed "sec1.tsv missing" because it ran alone, so the loop over the non S3 ports was skipped there; the SeaweedFS part ran (run 1 has the loop).
L4. The marker search covers /srv/s3/disk1/seaweedfs and /srv/s3/disk2/seaweedfs on each node only, not the system disk.
L5. No comparison between systems is made in this record. For RustFS see results/rustfs-vm-security-2026-10-11.txt: there the S3 port was the only data port and the plain object was found in clear (xl.meta), the
    SSE-S3 and SSE-C objects were not.
