STATUS OF THE HYPOTHESES OF THE FIRST RECORD
--------------------------------------------
H2 (GET partly from page cache): SUPPORTED for 1 MiB and 50 KiB (S2: drives deliver 11 to 39 percent of the client volume), NOT the case for 16 MiB and
   100 MiB (drives read 1.8 times the client volume). The cache was emptied before each run; why 1 MiB objects are cached and 16 MiB objects are not, although the
   datasets have the same size (about 8 GiB), is not known (untested ideas: a read path that bypasses the cache for large objects; the cache size per node of
   about 5.8 GiB available memory). So the 1 MiB and 50 KiB GET numbers must be labelled as measurements with a large cache share.
H4 (plateau caused by the load node): for large GET the load node network is a candidate limit (S3: 8.35 Gbit/s received, close to the 8.64 Gbit/s that iperf3 gave
   between nodes on 23 September for Ceph; today one iperf3 stream from ceph2 to ceph0 gave 5.05 Gbit/s), CONSISTENT WITH, NOT PROVEN; a test with
   parallel iperf3 streams into ceph2 would show the ceiling of the receive side.
   For PUT at high concurrency no resource of the three nodes is saturated (S5): the plateau cause is OPEN.
H3 (erasure coding cost makes PUT slow): NOT SUPPORTED as a CPU limit for PUT at 1 MiB (storage nodes about 55 percent busy); for 100 MiB PUT the load node is above 80
   percent (S4), so a CPU limit at ceph2 cannot be excluded there. Still OPEN.
H1 (fixed cost of about 50 ms per PUT from the write path): the drives write about 6 times the client data for 50 KiB (S1), so per object work on the drives is large;
   that the latency comes from synchronous flushes is NOT PROVEN. Settles: the RustFS documentation or source for its sync behaviour, and sar -d await and %util (not in
   this table).

NEW FINDINGS FOR THE THESIS
---------------------------
F-A. RustFS 1.0.1 on this setup writes about 6 times the client volume to the drives for 50 KiB objects (about 297 KiB on the drives per 50 KiB object: 44.4 MiB/s / 153.37
     objects per second), against about 2 times for large objects. (Ceph showed 1.73 times for 50 KiB, record of 24 September, a different mechanism.) Cause not examined.
F-B. For large objects (16 and 100 MiB) GET reads about 1.8 times the client volume from the drives, which is close to reading all six shards of the erasure set for each
     GET instead of the three that are needed. This is a read of the numbers, NOT proven (hypothesis: all shards are requested; settles: shard level read counters or a
     test with one node stopped).
F-C. 1 MiB GET at concurrency 4 and above is mostly served from memory (S2) and therefore says little about the drives.

LIMITS
------
L1. The load node is also a storage node, and in three configurations it is above 80 percent CPU (S4).
L2. sar %util, await and queue depth are not in the table (only rates), so a drive saturation cannot be excluded or shown here.
L3. The windows are the whole Warp process, so rates and ratios are approximate.
L4. Means of three runs per configuration; single run values are only in the per run tables on the nodes.
